## Formula and API audit

- Lower bank (`LMLF/Integral/Curve.lean:97–126`): `point u = -((R + u(ε-R)):ℂ)` runs from `-R` to `-ε`, its stored tangent is `R-ε`, and `logLift = log r - π I`.
- Inner circle (`:128–163`): `point u = ε exp(i(-π+2πu))` starts and ends at `-ε`, the tangent is `point * (2π I)`, and the lift is `log ε + i(-π+2πu)`. The increasing argument gives the required counterclockwise orientation and crosses the positive axis at principal argument zero.
- Upper bank (`:165–194`): `point u = -(ε + u(R-ε))` runs from `-ε` to `-R`, its tangent is `-(R-ε)`, and `logLift = log r + π I`.
- The `HankelRadii` structure (`:74–91`) enforces `0 < ε < R`; `OuterRadius ε` and `PositiveRadius` make invalid radii unavailable to either limit.
- `C1Contour` (`:17–46`) stores the tangent and proves `HasDerivWithinAt` on `Icc 0 1`, with continuous tangent, so the integral (`:36–40`) does not rely on an ambient totalized endpoint derivative. `LogLiftedC1Contour` stores continuity and `exp logLift = point` (`:48–55`), and its branch-aware integral uses the stored tangent (`:57–72`).
- `HankelContour` is an explicit three-piece structure with point joins (`:196–220`), and `HankelContour.Integrable` requires integrability on all pieces (`:222–226`).
- `HasHankelIntegral` (`:228–242`) requires every admissible finite contour to be integrable, takes the outer-radius limit over `OuterRadius ε` at fixed positive ε, then takes the `PositiveRadius` limit to zero. This correctly encodes the ordered DLMF improper limit.
- `HasHankelRepresentation` (`:244–250`) preserves the printed normalization directly: `value = normalization * integral`. The E2 theorem (`LMLF/Blueprint/Gamma/Section59.lean:40–49`) supplies `normalization = 1 / (2 * π * I)` and `value = 1 / Gamma z`, matching the source equation exactly.

## Findings

### P2 — The abstract `HankelContour` omits branch-lift join fields

`HankelContour` (`LMLF/Integral/Curve.lean:198–204`) records only `lower_join` and `upper_join` for the points. Its generic values could therefore have discontinuous log lifts at the joins, even though the concrete `hankelContour` has the matching formulas (`log ε - π I` at the first join and `log ε + π I` at the second). This does not undermine E2—the theorem uses the explicit constructor and the three public spec lemmas—but it makes the reusable structure weaker than the manual's “continuous logarithm carried along the contour” wording.

Add `lower_log_join` and `upper_log_join` fields, or expose named join lemmas for the concrete constructor. This is bounded API polish, not an acceptance blocker.

### P2 — The manual/manifest expose the piece formulas but not every composition declaration

`doc/LMLFManual/Chapter3.lean:328–395` and the E2 page show `HankelRadii`, the three `_spec` theorems, `HasHankelIntegral`, and `HasHankelRepresentation`, but do not display separate anchors for `HankelContour`, `hankelContour`, or `HankelContour.integral`. The manifest similarly lists the contour specs and `HankelContour.Integrable` but not all three composition declarations. Readers can reconstruct the E2 object from the displayed specs, and the anchors/build are valid, so this is a discoverability issue. Add those anchors if the composition layer is intended as public vocabulary; otherwise document it as an implementation composition.

### P3 — Figure 5.9.1 remains prose-only

The source inventory has `dlmf:5.9#F1@caption` for the Hankel contour diagram. The manual's prose and formulas now preserve the mathematical orientation and radius conventions, so no formula coverage is missing; adding the figure/caption link would nevertheless improve visual verification of the branch-side convention.
